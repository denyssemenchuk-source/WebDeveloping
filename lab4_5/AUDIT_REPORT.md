## 1. Дослідницькі завдання (§4)

### 1.1. Web Accessibility та WCAG 2.2 (§4.1)
- **4 принципи WCAG (POUR):**
  1. *Perceivable (Сприйнятність):* Інформація та компоненти інтерфейсу користувача повинні бути представлені у спосіб, доступний для сприйняття (текстові альтернативи, контраст, аудіоописи).
  2. *Operable (Керованість):* Інтерфейс користувача та навігація повинні управлятися з клавіатури, не викликати судом, надавати достатньо часу для взаємодії.
  3. *Understandable (Зрозумілість):* Текст має бути розбірливим і зрозумілим; робота сторінок — передбачуваною; користувачеві слід допомагати уникати помилок та виправляти їх.
  4. *Robust (Надійність):* Контент має бути достатньо надійним для інтерпретації широким спектром клієнтських програм, включаючи асистивні технології.
- **Що з'явилося саме у WCAG 2.2:**
  - `2.4.11 Focus Not Obscured (Minimum) (AA)`: Фокус не повинен повністю перекриватися плаваючими банерами чи фіксованими хедерами.
  - `2.5.7 Dragging Movements (AA)`: Для дій з перетягуванням має існувати альтернатива з одинарним кліком.
  - `2.5.8 Target Size (Minimum) (AA)`: Мінімальний розмір інтерактивної цілі — щонайменше 24×24 CSS px (або достатній відступ до сусідніх цілей).
  - `3.2.6 Consistent Help (A)`: Контактна інформація та довідка мають бути на одному й тому ж місці на різних сторінках сайту.
  - `3.3.7 Redundant Entry (A)`: Запобігання повторному введенню раніше наданої інформації в межах однієї сесії.
  - `3.3.8 Accessible Authentication (Minimum) (AA)`: Аутентифікація не повинна вимагати когнітивних функціональних тестів (розпізнавання об'єктів, розв'язання головоломок) без доступних альтернатив (копіювання пароля, автозаповнення).
  - *Вилучено:* Критерій `4.1.1 Parsing` визнано застарілим і вилучено, оскільки сучасні парсери HTML5 автоматично виправляють типові помилки синтаксису.
- **Порогові значення контрастності (WCAG 2.2 Level AA):**
  - Звичайний текст (менше 24px або менше 18.66px bold): **4.5:1** (Критерій 1.4.3).
  - Великий текст ($\ge 24\text{px}$ або $\ge 18.66\text{px}$ bold): **3:1** (Критерій 1.4.3).
  - Нетекстові елементи (рамки полів введення, іконки, стани UI): **3:1** (Критерій 1.4.11).
  - Розмір цілі (Target Size): **$24 \times 24$ CSS px** (Критерій 2.5.8).

### 1.2. Accessibility у Chrome DevTools (§4.2)
- **Accessibility Tree:** Дерево доступності відображає лише ті вузли DOM, які транслюються в платформенні Accessibility API (Role, Accessible Name, Description, States/Properties).
- **Експеримент:**
  - *Кнопка "Get started" (`#header-cta`):* До виправлення мала дублюючий `role="button"` і зайвий `aria-label="Get started button"`. Браузер читав: *Role: button, Name: "Get started button"*. Після заміни на `<a class="btn btn--primary" href="#trial">Get started</a>`: *Role: link, Name: "Get started"*, підтримує відкриття за `Enter`, фокусується штатно.
  - *Навігаційні пункти (`.nav-item`):* Були звичайними `<div>` без атрибутів. Вони взагалі не потрапляли у порядок табуляції клавіатури (`tabindex` відсутній) і не мали ролі у дереві доступності. Перетворені на семантичні `<a class="nav-item" href="#...">`.

### 1.4. Technical SEO Audit (§4.5 – §4.6)
- **Schema.org та JSON-LD:** Рекомендований Google формат структурованих даних. Для FlowTask використано `@type: "SoftwareApplication"` із вкладеними тарифними пропозиціями `offers` (`Basic $10`, `Pro $29`, `Enterprise $99`), що відповідають реальному контенту сторінки.
- **Open Graph Protocol:** Дозволяє генерувати привабливий сніпет (картку) у соцмережах (Facebook, LinkedIn, X, Telegram). Потрібні теги: `og:title`, `og:description`, `og:type="website"`, `og:url`, `og:image`.
- **robots.txt vs noindex:**
  - `robots.txt`: керує скануванням (*crawling*). Не дозволяє роботу витрачати crawl budget на закриті директорії. Заборона в robots.txt **не гарантує** вилучення з індексу Google, якщо інші сайти посилаються на цю URL.
  - `<meta name="robots" content="noindex">`: керує індексацією (*indexing*). Вказує роботу не додавати сторінку до результатів пошуку після завантаження.
  - *Критична помилка стартера:* У вихідному `robots.txt` було заборонено `/css/` та `/img/`. Googlebot вимагає доступу до стилів і картинок для якісного рендерингу сторінки (mobile-friendly test).
- **Розміщення robots.txt та sitemap.xml:**
  - Пошукові роботи шукають `robots.txt` виключно в корені origin: `https://example.com/robots.txt`.
  - На GitHub Pages проєкт знаходиться у підпапці (`https://<user>.github.io/<repo>/robots.txt`), де файл є просто звичайним текстовим файлом і не зчитується пошуковиком як директиви origin.
  - На Vercel деплой ведеться у корінь origin (`https://<project>.vercel.app/robots.txt`), тому robots.txt працює коректно.

### 1.5. Core Web Vitals (§4.7)
- **Метрики CWV (75-й перцентиль польових даних):**
  - **LCP (Largest Contentful Paint):** $\le 2.5\text{ с}$ (у проєкті — зображення `img/hero.jpg`).
  - **INP (Interaction to Next Paint):** $\le 200\text{ мс}$ (швидкість відгуку інтерфейсу на дію).
  - **CLS (Cumulative Layout Shift):** $\le 0.1$ (візуальна стабільність).
- **Чому INP відсутній у стандартному навігаційному звіті Lighthouse:**
  - Звичайний запуск Lighthouse вимірює лише процес первинного завантаження (navigation). INP є польовою метрикою реальних взаємодій користувача (кліки, тапи, натискання клавіш).
  - Лабораторним проксі для блокування головного потоку є **TBT (Total Blocking Time)**, але він фіксує лише блокування під час ініціалізації, а не затримку в обробниках кліків. Фактичну затримку взаємодії вимірюють у Chrome DevTools → вкладка **Performance** (запис трейсу з подією кліку).
- **Причини проблем у стартері:**
  - *Штучний лаг INP:* У функції `startSignup()` у `main.js` був навмисний блокуючий цикл `while (Date.now() - started < 300)`, що заморожував UI-потік на 300 мс.
  - *Джерело CLS:* У `main.js` через `setTimeout(..., 800)` після завантаження вставлявся промо-банер `.promo` нагору `document.body.firstChild`, що зсувало весь макет униз.

## 2. Результати початкового аудиту (§5.1)

- **Умови вимірювання:**
  - Vercel-деплой (`https://flowtask-audit.vercel.app/`)
  - Chrome 140, режим Інкогніто (без розширень)
  - Lighthouse Mobile, Throttling: Simulated Slow 4G, медіана 3 запусків.
- **Канонічний origin:** Обрано `https://flowtask-audit.vercel.app/`, оскільки Vercel надає корінь власного origin, що забезпечує коректну роботу `robots.txt`, `sitemap.xml`, а також узгодженість `canonical` та Open Graph URL.

### Виявлені дефекти стартера:
1. **Accessibility:**
   - Стиль `:focus { outline: none; }` вимикає видимий фокус на всіх елементах.
   - Колір `--ink-muted: #939ba7` на білому має коефіцієнт контрасту 2.64:1 (потрібно $\ge 4.5:1$).
   - Навігація виконана тегами `<div class="nav-item">` без `tabindex` та обробки клавіатури.
   - Кнопка `#hero-cta` була `<div class="button button--primary">` без фокусу й семантики.
   - Поля форми `#trial-form` не мали тегів `<label>` або `aria-label`.
   - Помилка валідації форми лише додавала рожеву тінь (немає текстового повідомлення чи `aria-invalid`, порушення WCAG 3.3.1 та 1.4.1).
   - Кнопки FAQ мали фіксований атрибут `aria-expanded="true"`, який ніколи не оновлювався у JS при згортанні/розгортанні.
   - Іконки в соціальних мережах у футері не мали назви (порожні посилання `<a href="#">`).
   - Порушення ієрархії заголовків: у секції `#features` використано `<h4>` замість `<h2>`.
2. **Technical SEO:**
   - Присутній мета-тег `<meta name="robots" content="noindex">`, що блокує індексацію.
   - Відсутні тег `<html lang="en">`, `meta description`, `canonical`, Open Graph теги.
   - `robots.txt` блокував `/css/` та `/img/`.
   - Був відсутній файл `sitemap.xml`.
   - JSON-LD описував неіснуючі параметри: назва "FlowTask Pro", ціна $19, фейковий рейтинг 4.9 з 1284 відгуками.
3. **Performance & Core Web Vitals:**
   - Зображення `hero.jpg` мало розмір 2.78 МБ без атрибутів `width` та `height` (викликало CLS та повільний LCP).
   - Відсутність `font-display: swap` для шрифту Inter.
   - Скрипт `main.js` блокував рендеринг у `<head>` без `defer`.
   - Динамічна вставка промо-банера викликала різкий стрибок CLS.
   - Блокуючий цикл у `startSignup` створював штучний лаг 300 мс (високий INP / Long Task).

## 4. Аналіз рекомендацій AI та відхилені поради (§5.3)

1. **Рекомендація 1 (Прийнято):** *Замінити `:focus { outline: none; }` на стилізацію `:focus-visible`.*
   - *Підтвердження:* Всі посилання та кнопки втрачали видимість при навігації клавіатурою.
   - *Джерело:* WCAG 2.2 Success Criterion 2.4.7 Focus Visible (Level AA).
   - *Рішення:* Реалізовано 2px outline фірмового кольору з відступом 2px.

2. **Рекомендація 2 (Прийнято):** *Видалити `meta name="robots" content="noindex"` та оновити `robots.txt`.*
   - *Підтвердження:* Тег прямо блокував сторінку для Googlebot, а заборона `/css/` порушувала рекомендації Google Search Central щодо рендерингу.
   - *Джерело:* Google Search Central — "Robots.txt Specifications" та "Understand Googlebot".

3. **Рекомендація 3 (Прийнято):** *Видалити 300 мс блокуючий цикл у `main.js` та перенести `.promo` у статичну розмітку.*
   - *Підтвердження:* Трейс DevTools чітко показував "Long Task" (300 мс) під час кліку та зсув макета CLS = 0.24 під час додавання банера.
   - *Джерело:* web.dev — "Optimize Interaction to Next Paint" та "Optimize Cumulative Layout Shift".

4. **Рекомендація 4 (Прийнято):** *Додати розміри `width="520" height="380"` та `fetchpriority="high"` для `hero.jpg`.*
   - *Підтвердження:* Браузер не знав пропорцій зображення до завантаження, що призводило до зсуву блоку. Зображення є LCP-елементом.
   - *Джерело:* web.dev — "Optimize Largest Contentful Paint".

5. **Рекомендація 5 (ВІДХИЛЕНО з обґрунтуванням):**
   - *Пропозиція AI:* Додати `role="button"` та `aria-label="Get started"` до всіх посилань та кнопок, а також обгорнути всі пункти меню в `role="menuitem"`.
   - *Чому відхилено:*
     1. **Перше правило ARIA (First Rule of ARIA):** Якщо можна використати нативний семантичний HTML-елемент (наприклад, `<a href="#trial">` або `<button>`), **не слід** додавати штучні ролі ARIA.
     2. Додавання `aria-label` до елементів із видимим змістовним текстом ("Get started", "Pricing") є надлишковим і може завадити автоматичному перекладу та локалізації.
     3. Навігаційне меню сайту не є меню десктопного додатку (application menu bar), тому використання `role="menu"` / `role="menuitem"` ламає стандартну поведінку скрінрідера для веб-навігації (нативна семантика `<nav>` та `<a>` є значно кращою).
   - *Джерело:* W3C WAI-ARIA Authoring Practices Guide (APG) — *No ARIA is better than Bad ARIA*.

## 6. Висновки

1. **Ефективність автоматизованих інструментів vs Ручний аудит:** Автоматичні інструменти (Lighthouse, axe-core) є чудовими для виявлення грубих порушень (відсутній `lang`, низький контраст, порожні посилання), проте вони не здатні виявити логічні помилки взаємодії, такі як статичний `aria-expanded`, відсутність реакції клавіатури на псевдокнопки чи затримки обробників подій.
2. **Роль AI-агента у веб-аудиті:** AI здатний швидко аналізувати структуру коду, знаходити приховані проблеми доступності та формувати детальні звіти. Однак критично важливо верифікувати кожну пораду за стандартами W3C WCAG 2.2, оскільки AI схильний генерувати надлишкові ARIA-атрибути там, де достатньо нативної семантики HTML5.
3. **Оптимізація Core Web Vitals:** Усунення синхронного блокування JS-потоку та забезпечення передбачуваних розмірів блоків дозволило досягти ідеальних показників швидкодії без зміни візуального дизайну сторінки.
